# Menus — نظام إدارة طلبات للمتاجر (Multi-tenant Store Ordering Platform)

نظام كامل لإدارة طلبات المتاجر أونلاين (مطاعم، كافيهات، سوبر ماركت، أو أي نوع متجر)، بيدعم أكتر من متجر على نفس المنصة (multi-tenant)، مع تطبيق زبون (PWA) وداشبورد لصاحب المتجر.

> **ملاحظة على المسميات بالكود:** الكود وقاعدة البيانات بيستخدموا مصطلح "restaurant/مطعم" بأسماء الجداول والمتغيرات (زي `restaurants`, `restaurant_id`) لأن المنصة اتبنت الأول لسياق مطاعم، لكن النظام عمليًا صالح لأي نوع متجر بيبيع منتجات ويستقبل طلبات (مطعم، كافيه، بقالة، محل هدايا، إلخ). لو بتوسّع الاستخدام، مش لازم تغيّر أسماء الجداول — كفاية تتعامل مع "restaurant" كمرادف لـ "متجر" بالنظام.

---

## 1. نظرة عامة (Overview)

المشروع عبارة عن Vanilla JavaScript (بدون فريموورك زي React/Vue) + Tailwind CSS + Supabase كـ Backend كامل (Database + Auth + Realtime + Storage).

فيه واجهتين رئيسيتين:

| الواجهة | الملف الرئيسي | المستخدم |
|---|---|---|
| **تطبيق الزبون** | `index.html` | العميل النهائي اللي بيطلب من المتجر |
| **داشبورد صاحب المتجر** | `dashboard.html` | صاحب/مدير المتجر لإدارة المنتجات والطلبات |

---

## 2. الـ Tech Stack

- **Frontend:** Vanilla JS (ES6+), Tailwind CSS (عبر CDN، مفيش build step)
- **Backend:** Supabase (Postgres + Auth + Realtime + Row Level Security)
- **خرائط:** Leaflet.js (لتحديد مواقع الفروع والتوصيل)
- **Push Notifications:** Web Push API + Service Worker (`sw.js`)
- **PWA:** قابل للتثبيت على الموبايل (`manifest.json`, `dashboard-manifest.json`)
- **Color picker (بالداشبورد):** Pickr

مفيش أي build tool (Webpack/Vite) — كل حاجة بتتحمل مباشرة بالمتصفح عبر `<script>` tags.

## 4. الإعداد والتشغيل (Setup)

### أ) إنشاء مشروع Supabase جديد
1. اعمل مشروع جديد على [supabase.com](https://supabase.com)
2. جيب الـ **Project URL** والـ **anon public key** من Settings → API

### ب) استيراد قاعدة البيانات
شغّل الـ migrations (شوف قسم "قاعدة البيانات" تحت) لإنشاء الجداول والـ RLS policies والـ functions.

### ج) تظبيط الإعدادات بالكود
افتح `core.js` ودور على السطرين دول (بالقسم `CONFIG`):

```js
const SUPABASE_URL  = 'https://xxxxx.supabase.co'
const SUPABASE_ANON = 'eyJ...'
```

غيّرهم بقيم مشروعك الجديد. **نفس التغيير لازم يتعمل جوا `dashboard.html`** (فيه نفس الإعدادات مكررة، لسه مش موحّدة بملف config واحد — نقطة تستاهل تحسين).

### د) التشغيل محليًا
مفيش build step، يعني تقدر تفتح `index.html` مباشرة بأي static server:

```bash
npx serve .
# أو
python3 -m http.server 8000
```

**مهم:** لازم static server مش فتح الملف مباشرة من الـ file system (`file://`)، عشان الـ Service Worker والـ PWA manifest محتاجين HTTP.

### هـ) رفع للإنتاج
أي static hosting بيشتغل (Vercel, Netlify, Cloudflare Pages, أو أي استضافة عادية). مفيش سيرفر Node/backend مطلوب — كل حاجة client-side بتتكلم مباشرة مع Supabase.

## 5. قاعدة البيانات (Database Schema)

كل الجداول تحت مظبوطة عليها **Row Level Security (RLS)**.

### الجداول الأساسية (مستخدمة فعليًا):

| الجدول | الوظيفة |
|---|---|
| `restaurants` | بيانات المتجر (الاسم، اللوجو، إعدادات الولاء، الاشتراك) — الاسم بالكود "restaurants" بس بيمثل أي نوع متجر |
| `branches` | فروع كل متجر |
| `categories` | فئات المنتجات |
| `products` | المنتجات (بأسعار، خصومات، إضافات، أحجام) |
| `bundles` | العروض المجمّعة (bundle offers) |
| `bundle_branches` | ربط العروض بالفروع |
| `banners` | البانرات الإعلانية بالصفحة الرئيسية |
| `orders` | الطلبات (حالة، عناصر، فاتورة، موقع التوصيل) |
| `order_returns` | طلبات الإرجاع/الاسترجاع |
| `menu_customers` | حسابات العملاء (مرتبطة بـ `auth.users`) |
| `coin_transactions` | حركة الكوينز (نظام الولاء) |
| `discount_codes` + `discount_code_redemptions` | أكواد الخصم واستخدامها |
| `push_subscriptions` | اشتراكات الإشعارات لصاحب المتجر (فيها `branch_id` — NULL = اشتراك أدمن يستقبل كل الفروع، قيمة = اشتراك فرع معيّن) |
| `customer_push_subscriptions` | اشتراكات الإشعارات للعملاء |
| `notifications` | سجل إشعارات العملاء (حالة الطلب، استرجاع، كوينز، عروض) |
| `merchant_notifications` | سجل إشعارات التاجر (طلب جديد، طلب استرجاع، إلغاء من العميل) — فيها `branch_id` بنفس منطق `push_subscriptions` |
| `dashboard_active_branch` | الفرع النشط لكل **جلسة دخول** (مش لكل حساب) — أساس نظام فصل الفروع، شوف قسم 6 |
| `reviews` | تقييمات المنتجات |
| `branch_products` | ⚠️ جدول موجود (توفر منتج معيّن لفرع معيّن) بس **مش مستخدم في أي مكان بالكود حاليًا** — لا الداشبورد ولا تطبيق العميل بيقروا منه أو يكتبوا فيه. لو محتاج الميزة دي فعليًا، تحتاج تُبنى من الصفر (واجهة إدارة + فلترة المنيو) |
| `platform_admins` | المستخدمين اللي عندهم صلاحية admin على المنصة كلها |
| `merchant_requests` | طلبات انضمام متاجر جديدة للمنصة |
| `subscription_plans` | باقات الاشتراك المتاحة للمتاجر |
| `audit_log` | سجل تدقيق للتعديلات اليدوية (أسعار، أرصدة) |
| `admin_alerts` | تنبيهات تلقائية (احتيال، أخطاء دفع متكررة) |
| `app_logs` | سجل أخطاء الفرونت إند (write-only، للـ debugging) — بيستقبل كمان أخطاء `order-action.html` (`app: 'order-action'`) |
| `auth_failed_attempts` | تتبع محاولات دخول فاشلة للداشبورد |

### ⚠️ جداول موجودة لكن غير مستخدمة حاليًا (0 صفوف):

`customers`, `customer_wallets`, `loyalty_points`, `coupons`, `coupon_usages` — دول شكلهم نظام قديم (legacy) أو نسخة تانية من نظام العملاء والولاء، اتبنى بس مش متوصل بالكود الحالي. الكود الفعلي بيستخدم `menu_customers` + `coin_transactions` بدالهم.

**لو بتبيع المشروع، وضّح ده للمشتري** — إما يشيلهم أو يكمل عليهم لو ناوي يستخدمهم مستقبلًا.

### Cron Jobs مجدولة:
- `auto_confirm_delivered_orders()` — بتأكيد استلام الطلب تلقائيًا لو العميل ماضغطش "تم استلام طلبي" بنفسه بعد مهلة محددة من وقت `delivering_at` (انتقال الطلب لحالة `delivered` قرار العميل حصريًا — مش قرار التاجر، لأن عليه بتتحسب الهدايا/الكوينز؛ شوف قسم 6)
- `detect_auth_failed_attempts()` — كشف محاولات دخول مشبوهة
- `detect_suspicious_order_frequency()` — كشف نشاط طلبات غير طبيعي
- `detect_payment_error_spike()` — كشف ارتفاع مفاجئ بأخطاء الدفع

## 6. تدفق تأكيد الطلب عبر واتساب (WhatsApp Order Action Flow)

لما عميل يعمل طلب، صاحب المتجر بياخد رسالة واتساب (قالب معتمد من Meta) فيها زرار برابط Edge Function. النظام ده مبني بحيث **القالب المعتمد من Meta ثابت ومتغيرش أبدًا** — أي تعديل أو ميزة جديدة بتتم بالكامل في الباك إند والصفحة الثابتة، من غير ما نحتاج نعرّض القالب لإعادة مراجعة من ميتا.

### ليه الموضوع معمول بالشكل ده أصلاً
Supabase (الخطة المجانية) بترفض ترندر HTML من دومين `*.supabase.co` — أي GET request بيرجع `text/html` بيتحول تلقائيًا لـ `text/plain`. فبدل ما نحتاج نرقّي لخطة Pro + Custom Domain، الحل كان:

1. **Edge Function `order-action`** (بيستقبلها زرار الواتساب): بترجع **302 redirect** بس (مفيهاش HTML خالص، فمش بيقع تحت قيد Supabase) لصفحة `order-action.html` المستضافة على GitHub Pages (نفس استضافة `index.html`)، مع تمرير `token` واسم المتجر (`r=slug`) في الرابط.
2. **`order-action.html`**: صفحة مستقلة بتكلم Supabase مباشرة بالـ anon key عن طريق مجموعة RPC functions، وتعرض كل حاجة للتاجر وتاخد قراره.

### الـ RPC functions المسؤولة (كلها `SECURITY DEFINER`، بتتحقق من التوكن بدل تسجيل دخول)

| الدالة | الوظيفة |
|---|---|
| `get_order_by_action_token(p_token)` | بترجع بيانات الطلب كاملة بناءً على التوكن |
| `resolve_order_action(p_token, p_action, p_reason)` | تأكيد/رفض الطلب وهو لسه `pending` — شاملة استرجاع المحفظة/الكوينز والإشعار للعميل لو رفض |
| `advance_order_status(p_token, p_status)` | تقديم حالة الطلب خطوة واحدة بس: `confirmed → ready → delivering`. **مش بتقبل `delivered` عمدًا** (شوف الملحوظة تحت) |
| `get_pending_return_by_token(p_token)` | بترجع طلب استرجاع "pending" لو موجود على نفس الطلب |
| `resolve_order_return_by_token(p_token, p_return_id, p_decision, ...)` | موافقة/رفض طلب استرجاع بالتوكن — غلاف فوق نفس المنطق اللي بيستخدمه الداشبورد |
| `_resolve_order_return_core(...)` | **دالة داخلية فقط** (من غير `grant execute`) — فيها منطق حساب الاسترجاع الفعلي (نسبة الأصناف، الخصومات، رسوم التوصيل). الداشبورد (`resolve_order_return`, بيتحقق `auth.uid()`) وصفحة الواتساب (`resolve_order_return_by_token`, بيتحقق التوكن) الاتنين بينداهوا الدالة دي، عشان يفضل مصدر الحقيقة واحد ومنكررش منطق الاسترجاع في مكانين |

### ⚠️ ملحوظة مهمة: "delivered" قرار العميل حصريًا
التاجر (من رابط الواتساب أو من الداشبورد) بيقدر يوصل بالطلب لحد `delivering` (تسليم المندوب) بس. الانتقال لـ `delivered` (تم الاستلام) **مقصود إنه يبقى بس من ناحية العميل** — يدوي (زرار "تم استلام طلبي" في `order-flow.js`) أو تلقائي بعد مهلة (`auto_confirm_delivered_orders` cron)، عشان الهدايا/الكوينز المرتبطة بإتمام الطلب تتحسب صح ومتبقاش تحت تصرف التاجر.

### حاجة معلّقة (Known Gap)
مفيش حاليًا أي **إشعار واتساب منفصل** بيتبعت للتاجر لما العميل يطلب استرجاع — الإشعار الوحيد (`send-order-whatsapp` edge function) بيتبعت بس عند إنشاء الطلب. يعني التاجر لازم يرجع لنفس رسالة الطلب الأصلية في واتساب عشان يشوف طلب الاسترجاع. لو حابب تضيف تنبيه فوري عبر واتساب، ده هيحتاج **قالب واتساب جديد يتعرض لمراجعة Meta**.

✅ **بديل موجود فعليًا (مش واتساب):** التاجر بياخد إشعار **Push + جرس في الداشبورد** فوري لما عميل يطلب استرجاع (`send-return-push` + جدول `merchant_notifications`)، وكمان لما عميل يلغي طلب بنفسه بعد التأكيد (`send-cancel-push`). شوف قسم 9 (نظام الفروع والإشعارات) للتفاصيل.

## 7. نظام الفروع (Multi-Branch System)

المتجر ممكن يكون عنده أكتر من فرع فعلي (جدول `branches`)، وده بيأثر على حاجتين مختلفتين خالص، مهم متتلخبطش:

### أ) فرع التوصيل (أي فرع يجهز طلب العميل)
- تطبيق العميل بيطلب موقعه **تلقائيًا وبصمت** أول ما صفحة المنيو تفتح (`requestAutoLocation()` في `core.js`) — من غير أي زرار أو اختيار يدوي. المتصفح بيسأل إذن الموقع **مرة واحدة بس** لكل عميل (بيتحفظ القرار بعدها).
- لو العميل وافق: موقعه بيتسجل تلقائيًا في نموذج الطلب، وأقرب فرع بيتحدد تلقائيًا وقت إرسال الطلب (`findNearestBranch()` في `order-flow.js`).
- لو رفض أو فشل التحديد: الصفحة بتفتح عادي زي ما هي (من غير أي إزعاج)، والعميل يقدر يحدد موقعه يدويًا وقت الطلب بالزرار الموجود في نموذج الطلب (نفس آلية ما قبل التحديد التلقائي).
- **مهم:** تحديد الموقع (تلقائي أو يدوي) دوره محصور في حاجتين بس: (1) عنوان واضح للمندوب، (2) حساب رسوم التوصيل. **مالوش أي علاقة بتغيير المنيو أو الصفحة المعروضة** — ده تصميم مقصود، الموقع مش بيغيّر المحتوى.
- ⚠️ **`table_number` (طلب من رقم طاولة) اتشال بالكامل من الكود** — كان حقل موجود بس مش متوصّل بأي حاجة (dead code)، مش فيتشر شغال. لو حابب فيتشر "اطلب من الطاولة" فعليًا مستقبلًا، محتاج يتبني من الصفر (رابط/QR مختلف لكل طاولة يحدد الفرع، مش رابط المتجر العام الحالي).
- ⚠️ **أسعار مختلفة حسب الفرع مش موجودة خالص.** جدول `products` فيه عمود سعر واحد بس مربوط بالمتجر ككل. لو محتاج أسعار مختلفة لكل فرع، ده مشروع منفصل محتاج جدول جديد (زي `branch_product_prices`) + واجهة إدارة في الداشبورد + منطق عرض يقرأ السعر الصح حسب الفرع.

### ب) فصل صلاحيات لوحة تحكم التاجر بين الفروع (Dashboard Branch Isolation)
ده مختلف تمامًا عن (أ) فوق — الموضوع هنا: موظف فرع معيّن يدخل الداشبورد بباسكود، ومفروض يشوف بس بيانات فرعه.

**المشكلة الأساسية اللي كانت موجودة:** الباسكود كان مجرد فلتر في الواجهة بس. أي جهاز داخل بدور "فرع" كان فعليًا جلسة Supabase Auth كاملة بنفس صلاحيات المالك (نفس `auth.uid()`) — يعني تقنيًا أي حد معاه باسكود فرع واحد بس، يقدر من الـ browser console يقرأ ويعدّل بيانات كل الفروع التانية.

**الحل المطبّق فعليًا:**
1. جدول `dashboard_active_branch` بيسجّل الفرع النشط **لكل جلسة دخول (session) على حدة**، مش لكل حساب — مهم عشان يدعم أكتر من جهاز/فرع شغالين في نفس اللحظة بنفس حساب المالك من غير ما يتلخبطوا في بعض. الجدول ده مربوط بجدول جلسات Supabase (`auth.sessions`) بـ `ON DELETE CASCADE`، فبيتنضف تلقائيًا لما الجلسة تنتهي.
2. `verify_dashboard_passcode` RPC (بعد التحقق الناجح من الباسكود) بتسجّل الفرع النشط في جلسة العميل الحالية.
3. **Custom Access Token Hook** (`custom_access_token_hook` function) — مفعّلة من Authentication → Hooks في لوحة تحكم Supabase نفسها (خطوة يدوية لازم تتعمل مرة واحدة، مش عن طريق SQL). بتحقن `branch_id` claim جوه التوكن (JWT) نفسه كل ما يتجدد، بناءً على آخر فرع اتحقق منه فعليًا بالباسكود.
4. RLS بتاعة `orders` بتتحقق من الـ claim ده مباشرة من التوكن (`auth.jwt() ->> 'branch_id'`) — مش من أي حاجة العميل بيبعتها من المتصفح.
5. `dashboard.html` بتجبر تجديد فوري للتوكن (`db.auth.refreshSession()`) بعد نجاح الباسكود مباشرة، عشان الصلاحية الجديدة تتفعل من غير ما تستنى تجديد تلقائي.

**ملحوظة مهمة عن الطلبات القديمة/غير المصنّفة:** RLS بتاعة `orders` بتعامل `branch_id = NULL` كـ "ظاهر لأي فرع" (مش مخفي) — لأن فيه طلبات حقيقية بترجع من غير فرع محدد (لو العميل رفض تحديد الموقع مثلاً)، وإخفاءها بالكامل عن كل الفروع كان هيبقى تراجع فعلي، مش تحسين أمان.

**جداول تانية اتفصلت بنفس المنطق (فرع أو NULL=أدمن يشوف الكل):**
- `push_subscriptions` — كل جهاز بيسجّل اشتراك push بفرعه، فالتنبيهات (طلب جديد/استرجاع/إلغاء) بتوصل بس لصاحب الفرع المعني + أي جهاز أدمن.
- `merchant_notifications` — نفس المنطق بالظبط لجرس الإشعارات في الداشبورد (تحميل، عداد غير مقروء، "تحديد الكل كمقروء"، والتحديث الفوري كلهم بيحترموا الفرع النشط).

**⚠️ ثغرة حقيقية اتصلحت (لازم الحفاظ عليها):** جدول `branches` نفسه فيه عمود `passcode`. كان فيه صلاحية SELECT على مستوى الجدول كله (blanket) لـ role الـ `authenticated` بتشمل العمود ده — يعني أي جهاز فرع (بنفس جلسة المالك الحقيقية) كان يقدر يقرأ باسكود **كل** الفروع التانية مباشرة عن طريق طلب REST مباشر (`?select=passcode`)، بغض النظر عن أي حماية في الواجهة. اتصلحت بـ:
```sql
REVOKE SELECT ON public.branches FROM authenticated;
GRANT SELECT (id, restaurant_id, name, lat, lng, is_active, created_at) ON public.branches TO authenticated;
```
يعني `passcode` دلوقتي مش قابل للقراءة **خالص** حتى من التاجر نفسه عبر الجدول مباشرة — القراءة الوحيدة المسموحة عن طريق `get_owner_secrets` RPC (بتتحقق من `owner_id = auth.uid()` قبل ما ترجع الباسكود). **مهم جدًا:** أي كود جديد يتعامل مع `branches` لازم يحدد الأعمدة صراحة (`select('id,name,lat,lng,...')`) وميستخدمش `select('*')` — لأن `select('*')` هيفشل بالكامل (مش بس يتجاهل العمود) طالما `passcode` مش من ضمن الصلاحيات.

**القيد المعماري المتبقي (قرار مستقبلي، مش عيب حالي):** بما إن كل أجهزة الفروع بتشارك نفس جلسة Supabase الحقيقية بتاعة المالك (الباسكود فلتر UI مش هوية منفصلة)، فأي تحقق أمان جديد هيفضل مبني على نفس الفكرة (JWT claim من `dashboard_active_branch`)، مش هوية Supabase مستقلة فعليًا لكل فرع. لو المتجر كبر وعايز فصل أعمق (صلاحيات مختلفة تمامًا لكل فرع، مش بس فلترة بيانات)، ده تغيير معماري أكبر (نظام دخول منفصل لكل فرع) يستاهل مشروع لوحده.

## 8. الأمان (Security Notes)

- **XSS Protection:** كل نص جاي من الداتابيز بيتعامل معاه بدالة `escapeHTML()` قبل ما يتحقن بالـ DOM (شوف `core.js`)
- **RLS:** كل الجداول محمية بـ Row Level Security — كل متجر بيشوف بياناته بس
- **Dashboard access:** صاحب المتجر بيدخل بـ passcode (`verify_dashboard_passcode` RPC) مش باسورد Supabase Auth عادي
- **فصل الفروع داخل نفس المتجر:** شوف قسم 7 بالتفصيل — نظام مبني على JWT claims + Custom Access Token Hook، مش فلترة واجهة بس
- **الـ anon key** موجود بالكود بشكل مقصود (ده طبيعي بمشاريع Supabase) — الحماية الفعلية بتيجي من الـ RLS policies **وصلاحيات الأعمدة (column-level grants)** مش من إخفاء المفتاح. مثال حي: عمود `branches.passcode` محمي بمنع صلاحية SELECT عليه تمامًا (لكل الأدوار)، مش بس RLS على مستوى الصف

## 9. حاجات لسه ناقصة / تستاهل شغل قبل البيع (Known Gaps)

- [ ] الإعدادات (`SUPABASE_URL`/`SUPABASE_ANON`) مكررة بأكتر من ملف — الأفضل ملف config واحد
- [ ] `dashboard.html` كبير جدًا ومحتاج يتقسم لملفات زي `index.html`
- [ ] الجداول القديمة (`customers`, `coupons`, إلخ) محتاجة قرار: تتشال ولا توضّح كـ "غير مستخدمة"
- [ ] `branch_products` جدول موجود بس مش متوصّل بأي حاجة — قرار: يتبني عليه (توفر منتج لفرع) ولا يتشال
- [ ] أسعار مختلفة حسب الفرع — مش موجودة خالص، مشروع منفصل لو مطلوب (شوف قسم 7)
- [ ] فصل الفروع حاليًا مبني على جلسة مالك مشتركة + JWT claim (شوف قسم 7) — مش هوية Supabase منفصلة فعليًا لكل فرع. كافي للاستخدام الحالي، لكن لو المتجر احتاج صلاحيات مختلفة تمامًا لكل فرع (مش بس فلترة بيانات)، محتاج مشروع أعمق
- [ ] مفيش automated tests
- [ ] الـ rate-limiting على الـ error logging بيحصل بالفرونت إند بس (سهل يتلف)، مفيش حماية على مستوى السيرفر
